# 今天吃什么助手：开发约定与分批实施计划

版本：1.0.0。适用基线：产品方案第6个保存版本、模拟数据1.0.0及独立文件交付版。

**目标：**据现有方案制作一个可操作、可核查、可交付的外卖助手Demo。本文件确定首版实施口径、模块边界和分批完成条件，可与产品方案及数据文件一起交给Codex执行。

**当前状态：**开发约定及计划已编制；模拟数据的21项推荐与19项购物车预期已经参考计算核对。产品代码、浏览器交互、真实模型调用和发布验收尚未完成，本文件中的各批次均为待实施任务。

## 二、首版范围与实现边界

### 1. 必须完成的能力

| 模块 | 首版要求 |
| --- | --- |
| 进入与示例 | 简化外卖首页入口；小A为默认用户；可切换其他用户和恢复示例 |
| 要求管理 | 长期、本餐、历史倾向可区分；支持手动编辑、历史建议确认、临时例外、撤销与清除本餐调整 |
| 推荐 | 供给和约束筛选、配置选择、稳定排序、主推及最多两个折叠备选、依据与未满足项 |
| 当次表达 | 在本章能力表内真实理解自然语言，支持必要澄清与冲突确认 |
| 历史备注 | 真实解析历史备注，展示来源和待确认建议；预置倾向需标明示例性质 |
| 商品操作 | 补齐规格、编辑辣度/份量/主食、同店加菜、数量修改、换店确认 |
| 模拟订单 | 订单核对、费用重算、模拟提交、重复提交保护；提交不自动写成已吃 |
| 恢复与异常 | 返回和刷新保持状态；无结果、售罄、地址/费用变化、AI失败均有后续操作 |

默认数据规模保持4家商家、12项主餐、8项加菜、2个地址、3组用户、6条历史。预算上限、到餐时间硬限制、AI生成推荐理由暂不纳入首版；解释由实际匹配结果生成。跨店组合、真实付款、账号系统及商家后台继续不做。

### 2. 自然语言与直接操作的分工

| 输入或操作 | 首版处理 | 边界与反馈 |
| --- | --- | --- |
| 不吃鸡肉、不要香菜等明确食材 | 识别词表中的食材排除，区分作用范围 | 未收录食材不能显示已过滤；提示当前无法核实 |
| 喜欢微辣、少油、少炸、想吃米饭/面、想吃小份 | 转为软偏好；明确“必须”“完全不能”时识别对应硬约束 | 使用数据契约的6个维度与允许值，不能新增隐含权重 |
| 本餐与长期设置 | 支持“今天”“以后”等范围表达；未说明默认本餐 | 已有硬约束冲突、取消或临时豁免须按规则确认 |
| 避开上一餐、避开昨天同餐、允许重复 | 转为既有重复规则 | 不扩展到一周、三天或自定义周期 |
| 撤销刚才修改、清除本餐临时要求 | 识别为两种独立需求操作 | 没有可撤销记录时明确提示，不改动其他状态 |
| 清淡点、不要太重口等模糊表达 | 提供少量含义选项或追问 | 不擅自转成完全不能吃辣；既有明确个人解释可复用 |
| “这份改小份”“微辣改不辣” | 通过所选商品的规格面板完成 | 首版不让模型定位购物车行并执行规格变更；提示“请在调整餐食中修改这份规格” |
| 换一个、查看备选、选餐、进店加菜、数量加减 | 使用对应页面控件 | “换一家”不作为自动排除商家的自然语言指令；引导查看备选选择其他商家 |
| 修改配送地址、日期、餐次 | 使用明确控件 | 模型不改地址；表达与当前餐次不一致时提示先核对餐次 |
| 预算、限时送达、营养目标或自动下单 | 首版未支持 | 明确说明未应用的部分，保留原条件，提供现有可用操作 |

“这餐想吃小份”改变推荐偏好，“把已经选的这份改小份”改变商品配置，两者不能混用。对一条输入中互相独立且可执行的部分可以应用，待澄清或未支持的部分分别展示；不能把整条消息显示为已成功处理。属于同一需求维度的歧义或冲突先整体暂缓该维度。

历史模式下的“今天”指对应历史订单那一餐。历史备注和当前用户输入必须在请求中明确区分；A21不能被当作今天的即时需求。

### 3. 历史整理的具体范围

示例启动时按mock-data.json载入已确认要求和historical_soft_preferences，保持R01等基线可复现。预置历史倾向标注“示例历史倾向”，不能称为本次模型分析结果。

首次整理该组备注时真实调用模型，返回饮食建议、历史归属线索、历史临时要求和履约备注。结果以“待确认建议”展示，尚未确认不改变基线要求与排序。明确仅指历史那餐的表达不自动推广为本餐或长期设置；已取消订单中的饮食备注也只作为待确认线索。

来源缓存键至少包含用户ID、历史内容版本和解析约定版本。历史内容未变化时复用；用户修改来源记录或主动重新整理时失效。首版不根据新订单自动增加新的历史偏好维度或训练长期画像；历史归属和用餐记录的纠正立即影响重复判断。

## 三、技术结构与项目约定

### 1. 默认实现方式

| 项目 | 采用方式 | 目的 |
| --- | --- | --- |
| 前端 | HTML、CSS、JavaScript ES modules | 与既有轻量网页方案一致，避免不必要框架 |
| 页面 | 单一应用内切换入口、助手、简化店铺、订单确认 | 共享状态，避免页面跳转丢失草稿 |
| 后端 | 默认Node.js轻量HTTP服务，同时提供静态页面和AI接口 | 同源访问；模型凭证留在服务端 |
| 规则 | 独立纯函数模块，不依赖DOM、网络或模型 | 可直接用R/C预期验收 |
| 状态 | 一个事件处理入口维护当前用户、任务与持久化 | 避免各页面维护互相矛盾的数据副本 |
| 持久化 | 浏览器本地存储，按数据版本和用户隔离 | 支持刷新、重复使用和恢复示例 |
| 模型 | 服务端可替换适配器，实际模型名由环境变量配置 | 不让页面或推荐逻辑绑定型号 |
| 资产 | 本地CSS、图标或占位图；首版不依赖外部图片URL | 数据中的image为null仍能完整展示商品 |

执行时先检查目标运行环境，选择其支持的Node.js版本，并记录在项目说明中。若已有项目环境要求其他运行时，可保留模块职责与接口契约进行等价实现，并记录差异。运行环境适配不能改变业务规则或增加服务范围。

本地启动命令约定为`npm start`；项目须提供对应脚本。实际安装步骤和所需版本写入生成的README，不预先宣称目标环境已经安装依赖。仅交付静态文件而没有可访问的AI服务，不能计为真实AI版本完成。

若保留上述目录，静态路由仅挂载public、可在浏览器运行的src/domain与src/state模块，以及mock-data.json；后两类使用明确的公开路径映射。src/ai、环境配置和其他服务器文件不进入静态路由。测试预期由测试进程读取，不作为前端推荐数据源。

### 3. 配置与运行模式

| 配置 | 用途 |
| --- | --- |
| PORT | 本地服务端口，默认3000 |
| OPENAI_API_KEY | 服务端模型凭证，不写入文件内容或前端 |
| FOOD_ASSISTANT_MODEL | 实际调用的模型名称；先沿用产品方案候选做连通性验证，再记录选定值 |

环境变量名称是本项目约定，实际模型请求格式在接入时按当时官方文档与账号能力核对。本文件不把候选型号或接口可用性当作已经验证的事实。

缺凭证时按disabled运行，显示“AI暂不可用，可直接编辑要求”，其他选餐流程可开发和体验。自动化测试可以注入确定响应，但仅在测试进程中启用；不得将固定样例响应包装成评审可见的真实AI。

## 四、状态与事件约定

### 1. 唯一状态模型

| 状态对象 | 需要保存的内容 |
| --- | --- |
| profile | 用户ID、已确认长期要求、示例历史倾向、历史纠正、待确认建议 |
| task | task_id、演示日期、餐次、地址、本餐条件、临时例外、跳过商品、当前页面 |
| selections | 商品的已展示预填与用户明确选择，保留来源，不能与比较配置混同 |
| cart | 商家、主餐行、加菜行、规格、数量、校验状态及当前费用 |
| requirement_change | 最近一次已生效需求修改的前后值及作用范围，用于单步撤销 |
| ai_request | request_id、task_id、条件版本、模式及加载/错误状态 |
| pending_changes | 尚待澄清或确认的操作；与已经生效的条件分开 |
| orders | 按task_id保存的模拟订单快照与submitted状态 |
| versions | 数据版本、条件版本、购物车版本、报价版本和缓存版本 |

推荐列表、比较配置和费用都是派生结果，不能作为另一个可独立编辑的事实来源。刷新时从保存的事实重算并校验；保存的旧报价不能直接当成新报价提交。

### 2. 必要事件与效果

| 事件 | 必须执行的变化 |
| --- | --- |
| ENTER_ASSISTANT | 载入当前用户与任务；已有有效草稿时提供继续入口 |
| APPLY_REQUIREMENTS | 校验操作、应用允许部分、保存单步撤销信息、提升条件版本、重算推荐和购物车状态 |
| CONFIRM_CHANGE | 仅应用用户确认的具体操作与范围；不扩大到未提及条件 |
| UNDO_LAST_CHANGE | 恢复最近需求操作前的相关字段，不撤销商品操作 |
| CLEAR_CURRENT_REQUIREMENTS | 清除本餐条件与临时例外，保持长期与历史基础，作为一次可撤销需求操作 |
| SKIP_PRODUCT | 将当前商品ID加入本餐跳过集合，不删除同主菜其他商家 |
| SELECT_MAIN | 创建或沿用主餐行；重复入口不追加数量 |
| EDIT_SPEC | 保存实际规格后重新校验，不修改比较配置来伪装用户选择 |
| ADD_ITEM/CHANGE_QUANTITY | 明确新增或修改数量；按角色、商品和规格保留关系 |
| REPLACE_MAIN | 同店换主餐保留加菜；换店先确认，确认后替换整车 |
| CHANGE_CONTEXT | 改地址、日期或餐次后重新检查供给、历史、费用，不清空既有选择 |
| SUBMIT_MOCK_ORDER | 校验最新内容和费用，保存一次模拟快照；重复请求返回本任务既有结果 |
| START_NEW_MEAL | 新task_id；清理本餐购物车、要求、例外、跳过记录和撤销记录；保留个人资料与有效历史 |
| RESTORE_EXAMPLE | 重置本演示数据的用户修改、草稿及新增模拟订单，重新锚定日期并恢复默认小A |

每次应用需求、地址、餐次或历史纠正都应使旧AI上下文失效。模型响应必须匹配当前用户、task_id、条件版本和仍有效的request_id；不匹配即丢弃，不展示已应用。只切换页面或查看备选不改变需求版本。

确认订单后如价格或商品变化，旧确认失效，展示变化并要求重新核对。提交按钮在请求处理中禁用；恢复后也按task_id查询已有结果。该保证用于本次本地模拟订单，不能描述为真实支付幂等保障。

### 3. 保存与切换

刷新恢复同一任务；开始新餐与恢复示例是不同动作。切换用户时保存当前用户草稿，载入目标用户各自资料；未完成AI请求失效，不能跨用户应用。恢复示例清理范围仅限本应用的版本化存储键。

数据版本不匹配时提示重置，不将旧字段当成当前结构直接使用；本地存储不可用时允许当前会话继续，并显示无法保存。历史建议缓存与当前会话状态分开，不能缓存上一次自然语言操作并重复执行。

## 五、AI接口与条件执行契约

### 1. 接口职责

| 接口 | 输入与输出 |
| --- | --- |
| GET /api/health | 返回服务状态、模型是否已配置；“已配置”不等于真实调用测试成功，不返回秘密值 |
| POST /api/interpret | 理解本餐表达或历史备注，返回结构化建议；不直接写购物车、提交订单或持久化用户资料 |

前端负责发出带版本的请求，服务端负责模型调用和结构校验，领域模块负责依据当前状态决定哪些操作可以生效、哪些必须确认。模型给出的“无需确认”不能覆盖程序判断。

### 2. 请求约定

| 字段 | 类型与要求 |
| --- | --- |
| request_id | 本次请求唯一字符串 |
| task_id | 当前任务标识；历史整理也必须关联发起任务，避免错误应用 |
| requirements_version | 非负整数，表示请求时条件版本 |
| mode | user_input或history_notes |
| text | 当前输入；历史模式可为空 |
| context | 当前已确认要求、本餐要求、临时例外、作用范围、餐次、可撤销信息和必要澄清上下文 |
| history_notes | 历史模式所需的记录ID、备注、相对时间、状态和归属；当前输入模式为空数组 |

允许词表由服务端读取受控的模拟数据，不信任客户端自行扩大。单次用户输入上限500字，超长时提示缩短；请求体上限64KiB。历史备注按既定6条示例发送，不发送完整地址、联系电话、支付信息或无关个人资料。

### 3. 响应约定

以下为应用内部统一返回格式，具体供应商响应由适配器转换。所有字段都需出现；没有内容的集合使用空数组，无对应值使用null。

```json
{
  "request_id": "req-example-1",
  "task_id": "task-example-1",
  "requirements_version": 3,
  "mode": "user_input",
  "status": "parsed",
  "operations": [
    {
      "op": "set_soft",
      "scope": "current",
      "field": "staple",
      "values": ["noodle"],
      "evidence": "今天想吃面",
      "source_record_id": null
    },
    {
      "op": "add_excluded",
      "scope": "current",
      "field": "ingredients",
      "values": ["chicken"],
      "evidence": "不要鸡肉",
      "source_record_id": null
    }
  ],
  "clarifications": [],
  "unsupported_parts": [],
  "record_annotations": [],
  "error": null
}
```

request_id、task_id、版本和mode由服务端从原请求回填，不能采用模型自行生成的身份信息。status只能是parsed、needs_clarification、unsupported或unavailable；返回parsed只表示解析完成，不代表用户条件已应用。

| 操作op | field与values | 生效规则 |
| --- | --- | --- |
| set_soft | 六个偏好维度之一，values为允许值数组 | 同维度替换，其他维度保留；按作用范围处理 |
| remove_soft | 对应偏好维度，values为空 | 删除指定范围该维度，按原规则回退到其他有效来源 |
| add_excluded | ingredients，values为词表食材ID数组 | 与已有有效排除合并 |
| remove_excluded | ingredients，values为具体食材ID | 仅移除指定范围；涉及明确排除的取消须核对范围与确认 |
| set_hard/remove_hard | 属性维度，设定用允许值数组、移除用空数组 | 程序核查已有约束冲突，不能覆盖其他要求 |
| set_repeat | repeat_rule，单个允许重复规则值 | 范围可为本餐或长期；放宽已有重复约束须明确确认 |
| propose_exception | ingredients或具体硬属性维度，values指出对应约束 | 仅提出本餐例外，不直接长期删除；先确认，再由领域模块应用 |
| undo_last | field为null、values为空、scope为current | 领域模块撤销最近一次需求修改，包括该次涉及的长期字段；scope表示当前任务命令，不是限制撤销字段范围 |
| clear_current | field为null、values为空、scope为current | 清除本餐要求和例外，不影响长期及历史 |

scope允许current、long_term、historical_meal、unresolved。历史模式必须带source_record_id并使用historical_meal或unresolved，不得直接输出已确认的长期/本餐变更。values仅允许字符串或布尔值，禁止把展示文本当成未定义枚举；空数组只用于移除或命令操作。

clarifications每项固定包含id、question、evidence、options，options为最多3个含id和label的解释选项；不能暗含用户未表达的限制。unsupported_parts每项包含evidence和reason。record_annotations每项包含source_record_id、belongs_to_user（true/false/null）、fulfillment_note（字符串或null）和evidence，用于历史归属线索与履约信息，不直接改写已确认记录；用户核对后才能修改记录归属。

error为null或包含code与message的对象。超时、上游不可用、格式失败、业务校验失败分别返回可区分错误。用户输入不能控制模型凭证、服务器路径、工具调用或系统指令；历史备注始终作为待解析数据。

### 4. 与24条语义用例的映射

| 用例 | 接口映射与检查重点 |
| --- | --- |
| A01—A04 | add_excluded及set_soft；A03拆成oil和fried两个维度，A04在晚餐上下文处理，不擅自切换餐次 |
| A05—A08 | long_term范围的排除、偏好、硬属性与重复设置 |
| A09—A12 | 局部替换/移除；A10同维多值最多一分；A11用remove_soft/current，删除本餐少油后按原长期设置回退并显示有效要求 |
| A13—A16 | undo_last、clear_current、remove_excluded/current及propose_exception；A16确认前必须不生效 |
| A17—A20 | needs_clarification；不擅自输出不辣硬约束 |
| A21—A24 | 历史作用范围、待确认排除建议、归属线索与纯履约信息；不直接改当前要求 |

供应商侧结构化Schema由开发者按以上字段生成并验证；接口测试使用真实请求和真实响应。可以变更供应商适配器，不能借此改变作用范围、确认条件或预期语义。若模型漏掉一个独立条件，必须计为该用例未通过，不能用静态映射补出“AI已理解”的结果。

### 5. 调用时机与失败策略

首次历史解析、提交自然语言、必要的澄清回复调用模型；换餐、展开备选、商品操作与结算不调用。历史已缓存且未改变时不重复调用。

默认不自动重试，避免重复建议和难以解释的等待；超时20秒后结束加载并保留原条件，用户可主动重试或手动编辑。同一任务只接受当前有效请求的结果。真实模型未配置或验证失败时，继续完成不依赖模型的批次，并在交付记录中把AI批次标为未通过/阻塞，不能改用固定响应后标为完成。

## 六、页面与视觉约定

### 1. 页面布局

采用移动优先布局，主要检查360px、390px、768px和1440px视口。桌面版在合理最大宽度内展开，不把手机页面无限拉宽。页面以选餐任务组织，输入框辅助调整，推荐卡片是主要内容。

| 界面 | 必须看见的内容与操作 |
| --- | --- |
| 简化首页入口 | “今天吃什么”与一句用途说明；点击进入助手，不能直接从补规格开始 |
| 助手页 | 地址、日期与餐次；有效要求摘要；本餐输入；一项主推、折叠备选；选餐/规格/加菜入口；已有草稿可继续 |
| 偏好面板 | 来源与作用范围、待确认历史建议、重复规则与相关记录、直接编辑、清除本餐、历史纠正 |
| 规格面板 | 当前商品支持的选项；已选/预填/待选标识；价格与冲突提示；保存和取消 |
| 简化店铺 | 少量同店商品及购物车；主餐和加菜关系可理解；增减、删改、返回和结算 |
| 订单确认 | 全部商品与实际规格、数量、地址、备注、费用、模拟提交标识；成功结果在本页显示 |

自然语言清楚表达的调整展示“已应用”及变更摘要；待确认、未处理和失败分别显示，不混成一个成功气泡。P09等商品的比较配置标注“参考配置，仍需选择”，不能让用户误以为已经选好主食。

### 2. 最低视觉与交互质量

默认使用浅色背景、深色正文、统一主色和一类强调色；主按钮、次操作与危险性重置操作保持视觉区别。采用清晰的商品名称、内容、价格、预计时间和2—3条相关理由，避免堆叠全部数据字段。

图片缺失时使用统一餐食占位，不显示破图或伪造外部图片。图标有文字含义；金额、冲突和状态不能只靠颜色表达。按钮支持键盘操作和可见焦点；面板关闭后焦点返回触发位置，表单具有标签。

数据或模型加载、空结果、规格缺失、无历史、冲突、失败和提交成功均有明确状态。错误不清空用户输入或有效草稿。输入期间不抢焦点；底部操作区不遮挡商品、金额或键盘输入区域。

### 3. 演示设置

独立设置区提供用户切换、恢复示例、商品售罄、配送费变化及模拟AI失败等触发器。日常流程只展示与用户任务相关的内容，演示触发器需标为模拟设置。

“模拟AI失败”仅用于验证恢复；不能提供伪装为真实AI的固定成功开关。报价变化后要求再次核对，恢复示例后默认回到小A、地址A01和既定午餐基线。

## 七、分批实施计划

每批形成可检查的代码、运行方法和结果记录，通过对应条件后继续。常规文件组织、样式与调试由开发者自主完成，不要求逐批人工批准。确需外部凭证或发布资源时，仅阻塞相关工作，其他批次继续推进。

### 批次0：确认输入和运行条件

**工作：**整理文件与目录；核对方案/数据版本；确认运行时；建立启动入口、环境变量示例和健康检查；使用参考脚本复核数据；有凭证时做一次模型连通性检查。

**产出：**可启动的项目骨架、README初稿、配置模板、输入版本记录及模型可用性记录。此批不制作完整页面。

**完成条件：**JSON可以加载，参考核对仍为40项通过，模型状态区分未配置、已配置未验证、实际连通成功/失败。缺凭证不阻塞批次1—3，但须登记为批次4的依赖。

### 批次1：规则、配置与费用

**工作：**实现需求合并、历史过滤、配置筛选、偏好计分、排序、备选去重及购物车核算，保持为可测试的独立模块。

**产出：**领域模块及读取独立预期的测试；不能从expected-results.json读取答案作为运行时推荐。

**完成条件：**产品自身实现通过R01—R21、C01—C19全部40项；核对完整顺序与展示顺序、未知信息过滤、P09比较配置、P05默认与明确选择的差异、硬属性不重复计分，以及主餐/加菜角色的费用。

参考Python脚本只作为交叉核对。即使复制了其中部分逻辑，也必须验证应用实际使用的模块；不得把参考脚本通过直接替代本批通过。

### 批次2：可独立完成的核心体验

**工作：**实现首页入口、助手首屏、推荐卡片、选餐、补规格、确认与模拟提交；连接批次1真实计算；提供基本布局和加载状态。

**产出：**本地可操作主流程，无需模型即可沿用小A要求完成选择；订单结果与页面状态一致。

**完成条件：**实际界面完成F01、F02、F12；P01直接进入确认，P09必须补选，订单数量与费用正确，同一task_id重复提交仍只生成一条模拟订单。

本批不得通过固定卡片和固定成功页绕过规则。尚未实现的AI输入明确提示未接入，不能显示伪造分析过程。

### 批次3：编辑、加菜与持久化

**工作：**实现偏好和历史编辑、单步撤销、清除本餐、临时例外确认、规格修改、店铺加菜、同店/换店行为、返回、刷新、用户切换和恢复示例。

**产出：**统一事件与状态管理、浏览器保存恢复、冲突提示和演示重置。待确认建议可先通过测试输入验证状态，不把该输入称为真实AI结果。

**完成条件：**界面完成F03—F09、F13、F14，并重新检查受改动影响的R/C用例。规格/数量变更后金额更新；需求变更不自动替换购物车；用户切换不串数据；开始新餐恢复长期要求。

新增补充检查：取消规格编辑不丢失原配置；本地存储不可用仍可完成当前任务；同一份商品的主餐和主动加菜在换餐后保持正确角色。补充用例使用D前缀编号，保持原有F编号不变。

### 批次4：真实AI理解与恢复

**工作：**实现/api/interpret、模型适配与校验；接入当次表达、历史备注、澄清和确认；处理过期响应、超时及未支持内容；记录实际模型名和调用范围。

**产出：**真实输入影响条件的AI功能、24条语义用例的实际响应与判定、必要的提示或校验修复记录。

**完成条件：**A01—A24按期望语义逐项执行并通过，实际界面通过F10、F11；新说法也能通过解析工作，不依赖完整输入字符串命中固定结果。关键范围误判、食材遗漏或确认绕过均判失败。

模型输出判定同时检查语义操作和最终条件效果；A17—A20正确澄清属于通过，A21—A24不应改变当前饮食要求。无可用模型凭证或持续接口失败时，本批标为阻塞/未通过，保留可操作手动模式并记录原因，不宣称完整AI交付。

### 批次5：异常、适配与正式交付

**工作：**完成售罄、地址不可配送、费用变化及无结果恢复；检查手机和桌面；按评审身份验证访问；整理源码、启动方法、测试记录和简短说明。

**产出：**可体验链接或可运行文件、最终README、实际验证记录、模型及模拟范围说明、已知限制。在线链接只在目标环境部署成功并实际打开后提供；当前不预先指定或虚构发布地址。

**完成条件：**F15通过，完整执行F01—F15的集成验收；核对本版最终代码对应的40项规则/费用结果及24项真实AI记录。设备检查至少覆盖360px、390px、768px和1440px，关键内容无遮挡、无横向溢出、操作可完成。

同源服务可作为默认发布形态；若目标平台要求分离静态页和AI服务，在保持接口与凭证边界的前提下适配。发布资源缺失时交付本地可运行成品与说明，在线访问单独标为未完成。
